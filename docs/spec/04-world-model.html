4 · World model

What the simulation knows. The sketches show shape, not final types.

4.1 Entities

Everything addressable is an Entity with a stable id, a kind and a location in the containment tree. The kind decides which state components it carries. That could be tagged unions or a light entity-component split. open

type EntityId = string & { readonly brand: 'EntityId' };

interface EntityBase {
  id: EntityId;
  kind: 'block' | 'building' | 'space' | 'portal' | 'item' | 'fixture' | 'character';
  name: string;              // canonical short name
  aliases: string[];         // parser/interpreter vocabulary
  description: string;       // authored or concretised; immutable once observed
  location: EntityId | null; // containment parent
  tags: string[];            // e.g. 'flammable', 'container', 'electrical'
}

4.2 Space

  • Block, the root. It contains buildings and outdoor spaces (sidewalk, alley, courtyard, roofs).
  • Building, which groups spaces and owns utility connections.
  • Space, a room or area with light level, noise and a public or private status for trespass rules.
  • Portal, which connects spaces: a door, window, stairs, fire escape or vent. It has open, locked and lock-key state and visibility/audibility through it, so the model knows who can see or hear what.

4.3 Things

  • Item, portable. It has weight and bulk, is optionally a container, and carries state (lit, filled…).
  • Fixture, not portable: an appliance, furniture or a utility endpoint. Appliances declare utility needs and behaviours.
  • Objects are driven by small, composable behaviours (container, lockable, powered, water-using, flammable, readable, edible…). Rules are written against behaviours, not individual objects. This is the immersive-sim approach and it is what makes unplanned solutions work.

4.4 Utilities

Following Spector's example of power and water supplies, utilities are graphs of sources → conduits → endpoints, such as mains → building panel → circuit breaker → sockets → kettle. State propagates each tick. Cutting a breaker kills the lights on a floor. A burst pipe floods the flat below. open Scope for v1 could be power and water, with gas, phone/internet and heating later.

4.5 Characters

interface Character extends EntityBase {
  kind: 'character';
  profile: {            // authored "who they are": stable, cacheable prompt material
    identity: string; background: string; personality: string[]; voice: string;
  };
  needs: Record<'hunger' | 'rest' | 'social' | 'money' | string, number>;
  schedule: ScheduleEntry[];            // routine: where/what by time of day
  goals: Goal[];                        // what they are trying to achieve, with plans
  relationships: Record<EntityId, Relationship>; // trust, affinity, history notes
  knowledge: KnowledgeRef[];            // facts this character believes (see 4.6)
  secrets: FactId[];                    // subset of knowledge they conceal
  inventory: EntityId[];
  status: { awake: boolean; activity: string; mood: string; health: number };
}

The player character is a Character too. Rules apply symmetrically, and NPCs can do almost anything the player can.

4.6 Facts, knowledge & memory

This is where the design lives or dies. It needs a single ledger of facts (true propositions about the world) and a per-character layer of beliefs:

  • Fact: a subject/predicate/object triple plus free text. Examples: "Mrs Okafor owes the landlord three months' rent" or "the key to 3B is under the mat". Facts have provenance, meaning the event that established them.
  • Belief: a character's reference to a fact, or to a false proposition they hold, with source (witnessed, told-by, inferred), confidence and time learned. Lies and rumours are false beliefs.
  • Memory stream: per character, a timestamped log of observations. Importance scoring and periodic reflection condense it into higher-level beliefs, following the Generative Agents pattern.
  • Perception: events are delivered to the characters who could perceive them, based on the same space or portal visibility/audibility, awake or asleep, and attention. This is how gossip, witnesses and alibis emerge.

4.7 Time

  • A world clock in minutes. Each action has a time cost. open The default granularity could be 1 turn ≈ 1–5 minutes, with wait and sleep to skip.
  • Off-stage residents are simulated at a coarser granularity, following their schedules. On-stage residents are simulated per turn.
  • Day/night, opening hours and weekly rhythms such as rent day and bin day provide natural pressure.

4.8 Events

interface WorldEvent {
  seq: number; at: GameTime; kind: string;       // 'moved' | 'took' | 'said' | 'power-cut' | …
  actor?: EntityId; targets: EntityId[];
  payload: unknown;                              // kind-specific, schema-validated
  cause?: { by: 'player' | 'rule' | 'schedule' | 'character-mind' | 'director'; ref?: string };
}

4.9 Where the block comes from

open There are three options:

  • (a) A hand-authored block data file.
  • (b) An LLM-generated block at new-game time. It gets validated, frozen and then treated as authored.
  • (c) A hybrid, where an authored skeleton of layout and key residents gets LLM-filled detail.

My recommendation is (a) for a first vertical slice, because it gives us a fixed test fixture. Build (b) or (c) later on the same schema.
