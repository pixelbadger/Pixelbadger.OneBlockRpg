7 · Game payload

How a user's story becomes a loadable game: a data package, validated against a published schema, that a coding agent can produce.

7.1 Workflow

  1. The user writes a story brief (7.2): plot, characters, relationships and tensions, trigger points.
  2. A coding agent builds the payload from it. That covers the block layout, every room and object, all flavour text, behaviours, conversation specs, hooks and triggers. It follows the payload authoring guide (7.9).
  3. oneblock validate checks the schema, references and playability (7.7) and returns errors the agent can fix.
  4. oneblock play loads it. Scripted playthroughs (§3.6) act as the payload's tests.

7.2 The story brief

The brief is the human's input. It is prose or light structure, and the agent turns it into the payload. Expected sections:

Premise & toneSetting, era, mood, how strange it getsstory.synopsis, style guide, all flavour text
General plotWhat is going on, and the arc if the player does nothingSynopsis, character goals, timed triggers
CharactersWho they are, what they want, what they hideCharacters: personas, SPECIAL and tag skills (§5), goals, beliefs, routines, combat profiles, essential flags
Relationships & tensionsWho owes, loves, fears or suspects whomRelationship values, beliefs, conversation goals, hooks
Trigger pointsKey plot beats and what sets them offTriggers (7.6), pinned conversation options
Set piecesBig scenes: the player's loose objective, who's involved, what should happenSet pieces with director brief, beats and allowed moves (§6.7)
EndingsHow it can endEnding triggers

7.3 Layout

my-block/
  game.yaml            # id, title, schemaVersion, start room, player character, clock start, style guide
  story.yaml           # synopsis, tensions, triggers, endings
  rooms/*.yaml
  objects/*.yaml       # incl. use rules; weapons, armour, consumables (§5.7); sleepable furniture
  characters/*.yaml    # persona, SPECIAL, tag skills, goals, relationships, beliefs, behaviours, combat profile
  conversations/*.yaml # conversation specs (§6.2)
  hooks.yaml           # hook catalogue (§6.4)
  behaviours/*.yaml    # shared behaviours (§4.5)
  callouts.yaml        # scripted LLM callouts (§6.5)
  set_pieces/*.yaml    # director-run scenarios (§6.7)
  combat_text.yaml     # hit / miss / crit / down message templates per weapon type (§5.6)

Files are YAML (comments help agents and humans) or JSON, validated against one JSON Schema generated from the engine's zod types. The split across files is a convention. The loader merges everything, and ids are global.

7.4 Text variants

All flavour text is authored. Any description can be a single string or an ordered list of variants. The first variant whose condition holds is used.

description:
  - when: { flag: power_out }
    text: "The stairwell is black. Somewhere above, a radio keeps playing."
  - when: { special: { PE: { gte: 7 } } }
    text: "Fluorescent hum. Fresh scratches around the lock of 3B."
  - text: "Fluorescent hum, scuffed lino, the smell of someone's dinner."

Text can interpolate state ({{clock.time}}, {{objects.kettle.temperature}}) but has no logic beyond that.

The language is deliberately not Turing-complete: no loops, no variables, no arbitrary code. If an effect is genuinely missing, it gets added to the engine and the schema, not scripted around.

7.6 Triggers: plot points

# story.yaml
synopsis: >
  The landlord of 41 Carver Street is quietly selling the building. Mrs Okafor, the caretaker, knows.
  Someone in 3B has been receiving letters with no stamps…
tensions:
  - "Okafor protects the tenants but needs this job"
  - "Dev (3B) and the landlord share a secret older than the building"
triggers:
  - id: eviction-notices
    when: { all: [ { day: { gte: 3 } }, { not: { flag: sale_stopped } } ] }
    do:
      - { narrate: "Envelopes have appeared under every door." }
      - { spawn: { object: eviction-notice, in: player-flat } }
      - { set_flag: act_2 }
    once: true
endings:
  - id: the-block-holds
    when: { flag: sale_stopped }
    text: "…"

7.7 Validation

  • Schema: types, required fields, enums.
  • References: every id referenced exists, and ids are unique.
  • Playability lint: every room is reachable from the start, every flag a trigger reads is set somewhere, every hook a conversation lists exists, at least one ending is reachable, and every text variant list has an unconditional fallback. Set pieces must have reachable end conditions and only reference cast and stage that exist. Every weapon type needs combat text. Every conversation granting attack is flagged for review.
  • Mechanics lint: SPECIAL values are in 1–10, weapon minimum ST is achievable, and every character can reach something sleepable or has sleep in their schedule.
  • Budget lint: warns on oversized personas, synopses or director briefs, since they are in every relevant prompt.
  • Errors give the file, path and a suggested fix, so an agent can iterate on its own.

7.8 Versioning

game.yaml declares a schemaVersion. The engine loads matching major versions. Saves record payload id and version, and a changed payload invalidates saves unless it is marked compatible.
