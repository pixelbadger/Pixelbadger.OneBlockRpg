6 · LLM layer

Where the LLM works: conversations, set pieces, callouts, reading and day summaries. Also the memory model and provider interface underneath them.

6.1 Scope

The LLM is used in five places only:

  1. Conversations voice a character, choose its actions and hooks, and suggest player options (6.2–6.6).
  2. Set pieces run a director that orchestrates a declared scenario (6.7).
  3. Scripted callouts are payload-declared one-off generations (6.5).
  4. Day summaries condense each character's day when the player sleeps (6.8).
  5. Reading: a character weighs what a document says against what they already believe (6.11).

All other text is authored in the payload. All other behaviour, including NPC combat decisions, is scripted (P5).

Content boundaries (Q14): the engine adds no content filter of its own. LLM output is governed by the payload's tone and style guide, and by the provider's own policies. A refusal is handled like any other invalid output (6.9).

6.2 Conversation specs

The payload declares conversations per character. Each spec gives the LLM a frame, and gives the engine its guard rails.

conversations:
  - id: okafor-rent
    character: okafor
    when: { flag: rent_overdue }                # availability condition
    goals:                                      # conversation-specific, on top of the character's high-level goals
      - "Get the player to promise to pay by Friday"
      - "Do not reveal that the landlord is selling the building"
    opening: "Mrs Okafor leans on her broom. 'You. Rent.'"
    options:                                    # authored player options, merged with LLM ones
      - text: "[Speech] I can get you the money, but I need to know why the rush."
        when: { special: { CH: { gte: 6 } } }
        check: { skill: speech, tier: hard,
                 pass: [ { add_belief: { who: player, belief: landlord-selling } } ] }
      - text: "I'll pay Friday."
        effects: [ { set_flag: promised_rent }, { end_conversation: {} } ]
    hooks: [ reveal-landlord-sale, adjust-trust ]   # what the LLM may invoke
    actions: [ go, give, take, attack, use ]        # which actions the character may take here (6.6)
    ends_when: { any: [ { flag: promised_rent }, { turns: { gte: 12 } } ] }

6.3 A conversation turn

Each character turn is one structured LLM call. The context is ordered from stable to volatile so prompt caching works:

  1. Engine rules and style guide (fixed)
  2. Story synopsis and tone (per payload)
  3. Persona, SPECIAL and derived stats, high-level goals, relationships (per character)
  4. All previous day summaries for this character (6.8; this part only changes overnight)
  5. Conversation goals, hook and action catalogue, current beliefs (per conversation)
  6. Today's log for this character, the transcript so far, and the results of the last actions, hooks and checks (per turn)
interface CharacterTurn {                // structured output, validated with zod
  line: string;                          // what the character says; tone unbounded
  emotion?: string;
  actions: ActionRequest[];              // 6.6: physical actions, e.g. give the key, walk out, throw a punch
  hooks: { id: string; args: Record<string, unknown> }[];
  playerOptions: {                       // 2–4 suggestions, merged with authored options
    text: string;
    action?: ActionRequest;              // e.g. "[Hand over the envelope]"
    check?: { skill: SkillId; tier: Tier };   // e.g. "[Speech] You're lying." — engine rolls
  }[];
  wantsToEnd?: boolean;
}

The engine resolves the character's actions and hooks, then merges player options. Authored options win ties. Gated options show their gate ([Speech], [CH 6]). The player can always leave. There is no free-text "say something else" option in v1 (Q20).

6.4 Hooks: where the constructed touches the ground

hooks:
  - id: reveal-landlord-sale
    description: "Okafor admits the landlord is selling the building."   # shown to the LLM
    guard: { relationship: { who: okafor, with: player, trust: { gte: 60 } } }
    effects: [ { add_belief: { who: player, belief: landlord-selling } }, { set_flag: sale_known } ]
    once: true
  • Hooks change story state (flags, beliefs, relationships, spawning, starting set pieces). Physical acts use actions (6.6).
  • The LLM chooses whether and when to use a hook. The engine checks the guard and applies it. A failed guard is reported back so the character can react.
  • Anything said without a hook is speech. It is remembered (6.8), but it is not fact.

6.5 Scripted callouts

A callout is a payload-declared LLM generation for moments where authored text would be too rigid, such as a dream or a radio broadcast. It is fired by a trigger or behaviour effect.

callouts:
  - id: dream-sequence
    prompt: "Render the player's dream tonight, drawing on: {{summaries.player.today}}. Magical realism; 80–120 words."
    output: text
    cache: per-save                  # generated once per save, then fixed

6.6 Character actions in conversation

Characters can do things mid-conversation, using the same action vocabulary as everyone else (§4.3). Each one is checked and resolved by the engine:

type ActionRequest =
  | { act: 'give'; item: ObjectId; to: ObjectId }
  | { act: 'take'; item: ObjectId; from?: ObjectId }   // from a character → needs consent, a Steal check, or a downed target
  | { act: 'go'; to: RoomId }                          // leaving ends the conversation unless followed
  | { act: 'attack'; target: ObjectId; weapon?: ObjectId }   // starts combat (§5.6)
  | { act: 'use' | 'open' | 'close' | 'drop' | 'equip'; target: ObjectId; on?: ObjectId };
  • Allow-list. The conversation spec lists which actions are allowed. The default is go, give, take, use, and attack must be granted explicitly.
  • Validation is the same as anywhere else: possession, location, carry capacity, AP and SPECIAL. Failures are reported back on the next turn ("she reaches for the key, but it isn't in her pocket").
  • Attack suspends the conversation and enters combat. Afterwards the conversation may resume if both parties are conscious and the character is willing. The resumed turn sees the combat outcome.
  • Time spent on actions is added to the conversation's duration.

6.7 Set pieces and the director

A set piece is a payload-declared scenario: the player gets a loose objective, and an LLM director orchestrates the cast to make it play out. It is the only place a director exists, and its scope is bounded by the declaration.

set_pieces:
  - id: the-fire
    starts_when: { all: [ { flag: act_2 }, { time: "02:00" } ] }
    objective: "Get everyone out of the building."         # shown to the player, loosely
    stage: [ stairwell, hall-2, flat-2b, flat-3b, street ]
    cast: [ okafor, dev, mr-pike ]
    director_brief: >
      Panic and revelation. Dev should try to go back for the letters; Pike blocks the stairs
      until someone persuades or forces him. Somebody should see something they shouldn't.
    beats: [ alarm, smoke-spreads, the-letters, the-way-out ]   # ordered, director chooses pacing
    moves:                                                    # what the director may do
      actions: [ go, give, take, use, attack ]                # on behalf of cast members
      effects: [ narrate, set_property, set_flag, add_belief ]
      hooks: [ fire-spreads, stairwell-collapses ]
    ends_when: { any: [ { flag: building_evacuated }, { time_after: "03:00" } ] }
    outcomes:
      - when: { flag: building_evacuated }
        do: [ { award_xp: 300 }, { set_flag: fire_survived } ]
  • Cadence (Q29). After each player turn inside the set piece, the director gets one call. It sees the brief, the beats so far, the stage state and the cast's SPECIAL and goals. It returns cast actions, effects, hooks, narration (unbounded in tone) and beat progress. All of it is validated as usual.
  • Conversations inside a set piece get the director brief and current beat in their context, so characters stay in the scene.
  • Combat inside a set piece uses §5.6. The director may set cast targets and intentions between rounds.
  • On end, an outcome summary goes into every participant's day log.

6.8 Memory: days are chapters

  • During the day, each character keeps a day log: structured entries for the conversations they had or overheard (full transcripts, §3.3), events they witnessed, actions taken on or near them, hook results and set-piece outcomes. Conversations within the same day see the raw log.
  • When the player sleeps (§5.8), the day ends. Each character who had activity gets one summary call, producing a bounded day summary (target ≤ 250 words) written in their own perspective. It records what they now think of people, what was promised, and what they suspect. The player gets one too, which can be shown as a journal on waking.
  • All previous day summaries are put at the front of that character's context in every later call (6.3). Summaries are per character, so a character never knows what they didn't experience.
  • Structured state outranks summaries. Flags, beliefs and relationships set by hooks are authoritative. Summaries carry tone and detail.
  • Raw logs are kept in the event log for replay and debugging, but never fed back into prompts after their day.
  • Safety valve: if a single day's log outgrows its budget (a very talkative day), older entries in it are summarised early. Old day summaries are not rolled up into chapter summaries in v1 (Q28). Revisit if games run past ~2–3 weeks of in-game time.

6.9 Provider interface

interface LlmProvider {
  readonly id: string;               // 'claude-subscription', 'anthropic-api', 'scripted', 'replay', …
  readonly capabilities: { structuredOutput: boolean; promptCaching: boolean; streaming: boolean; maxContextTokens: number };
  complete<T>(req: CompletionRequest<T>): Promise<CompletionResult<T>>;
}
interface CompletionRequest<T> {
  purpose: 'conversation' | 'director' | 'callout' | 'day-summary' | 'reading';
  system: PromptPart[];              // ordered stable → volatile
  messages: { role: 'user' | 'assistant'; content: string }[];
  schema?: ZodType<T>;               // validated engine-side regardless of provider
  maxOutputTokens?: number;
}
  • Invalid output gets one retry, then a safe fallback. A conversation falls back to an authored "they don't answer" line plus authored options. A director falls back to a no-op turn, so the set piece continues on behaviours. A turn never crashes.
  • refusal stop reasons are handled the same way.

6.10 Cost

LLM calls happen once per conversation turn, once per player turn inside a set piece, once per callout, and once per active character each night. Exploration and ordinary combat are free. Day summaries keep context growth linear and small, at roughly 250 words per character per day. Usage is logged per purpose so that model choice can be based on measurements.

6.11 Reading: reconciling what a document says

A document declares the beliefs it teaches (§4.13). The player takes in what they read: the player decides what to make of it, and their beliefs drive the story's own triggers. A character who reads something new doesn't simply absorb it. Examining it raises a read signal, and the narrative layer makes one reading call in that character's perspective: the story, their persona and SPECIAL, their memory of previous days, today's log, what they believe now (with confidence and source), the document's full text and its propositions (the taught beliefs).

The prompt frames the decision as cognitive dissonance. What fits goes in easily. What contradicts a firm or important belief is resisted, and the discomfort is resolved in one of the ways people resolve it: change your mind (accept it, weaken or drop what it contradicts), discount the source (a forgery, gossip, an agenda), reinterpret it to fit ("this proves their side is wrong"), or shelve it. Intelligence decides how fully the reader follows the text, not how credulous they are. One call does all of it:

{ "reaction": "Abroad? Convenient. But the deeds, those I believe.",
  "accept":   [{ "belief": "deeds-forged", "confidence": 0.8 }],               // taught beliefs only
  "revise":   [{ "belief": "landlord-guilty", "confidence": 1 },               // beliefs already held:
               { "belief": "pike-is-honest", "drop": true }],                  //   re-weigh or drop
  "thoughts": [{ "text": "Someone wrote this to clear the landlord's name.", "confidence": 0.7 }] }
  • The engine validates the verdict and applies it as belief-added and belief-removed events (cause reading). Only taught beliefs can be accepted and only held beliefs revised; confidences are clamped to 0–1.
  • Thoughts (at most two) are beliefs in the character's own words, with ids thought-1, thought-2… They appear in that character's later prompts (conversations, summaries, further reading) but no condition can test them: story ids stay the only mechanical anchor, so the constructed reaches the ground only through beliefs the author declared.
  • A read event (targets: the document; payload: accepted, rejected) lets behaviours react to what was accepted or refused, and the reaction goes in the character's day log.
  • Knowing is not believing. Whatever the verdict, the engine has already recorded that the character read the document (the read condition, §7.5). Author what they do with what they read on read, and let believes only change how they do it: Gary tells the pub about the register either way, as a ghost story or as a curiosity.
  • Fallback (6.9; also offline): the character takes in every taught belief at confidence 1, which is how reading worked before.
