5 · LLM layer

Provider interface, roles, grounding and cost.

5.1 Provider interface

Core code talks to one small interface. Providers declare what they can do, and the engine degrades gracefully when a capability is missing.

interface LlmProvider {
  readonly id: string;                       // 'claude-subscription', 'anthropic-api', 'scripted', …
  readonly capabilities: {
    structuredOutput: boolean;               // native JSON-schema constrained output
    promptCaching: boolean;
    streaming: boolean;
    maxContextTokens: number;
  };
  complete<T>(req: CompletionRequest<T>): Promise<CompletionResult<T>>;
}

interface CompletionRequest<T> {
  role: LlmRole;                             // for routing, budgeting and cassette keys
  system: PromptPart[];                      // ordered stable → volatile (cache-friendly)
  messages: { role: 'user' | 'assistant'; content: string }[];
  schema?: ZodType<T>;                       // when set, result.value is validated T
  tier?: 'fast' | 'smart';                   // provider maps to a concrete model
  maxOutputTokens?: number;
}

interface CompletionResult<T> {
  value: T | string;  text: string;
  usage: { inputTokens: number; outputTokens: number; cachedInputTokens?: number };
  stop: 'end' | 'max_tokens' | 'refusal' | 'error';
}
  • When a provider lacks native structured output, the engine falls back to a "respond with JSON matching this schema" prompt followed by parse, validate and retry once. Validation always happens engine-side with zod, whatever the provider claims.
  • A refusal or invalid output MUST degrade to a safe default, such as a neutral narration or an "X doesn't respond" line. It must never crash the turn or corrupt state.

5.3 Roles

Each role is a separate prompt contract with its own output schema. Roles never share a free-form conversation. Each call is rebuilt from world state, which keeps calls stateless and replayable.

RoleInputOutput (schema)Tier

NarratorThis turn's perceivable events, scene entities, style guideProse, plus the ids of entities mentioned (checked against scope)smart

5.4 Grounding rules

  • Epistemic filtering. A Character call receives only that character's beliefs. It never sees the fact ledger. A revealedFacts entry the character doesn't hold is rejected.
  • Scope filtering. The Narrator gets only what the player can perceive. Mentioned entity ids outside scope trigger a regenerate or a strip.
  • Action proposals are requests. For example, "Hands over the key" becomes a give action that the rules validate. If the character doesn't have the key, the action fails and the utterance is re-rendered or annotated.

5.5 Prompt layout & cost

  • Order prompt parts from stable to volatile: engine rules and style guide, then the block bible, then the character profile, then current state, then this turn. This maximises prefix caching where the provider supports it.
  • A per-turn LLM call budget. A typical turn is 1 interpreter call (often skipped by the fast-path parser) + 1 narrator call, plus 1 per addressed character. Off-stage residents cost nothing, since they are rule-driven. Reflection and direction are amortised.
  • Usage is logged per role so we can tune model tiers and budgets using measurements.
