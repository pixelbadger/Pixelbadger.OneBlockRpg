5 · Conversation & LLM layer

Where the LLM works: conversations and declared callouts. It also covers the provider interface underneath both.

5.1 Scope

The LLM is used in two places only:

  1. Conversations: voicing a character, proposing player options and choosing hooks (5.2–5.4).
  2. Scripted callouts: payload-declared LLM calls fired by triggers or behaviours for special moments (5.5).

All other text is authored in the payload (P5). An optional summarisation call condenses transcripts into memories when a conversation ends.

5.2 Conversation specs

The payload declares conversations per character. Each spec gives the LLM a frame, and gives the engine its guard rails.

conversations:
  - id: okafor-rent
    character: okafor
    when: { flag: rent_overdue }                # availability condition
    goals:                                      # conversation-specific, on top of the character's high-level goals
      - "Get the player to promise to pay by Friday"
      - "Do not reveal that the landlord is selling the building"
    opening: "Mrs Okafor leans on her broom. 'You. Rent.'"   # optional authored first line
    options:                                    # authored player options, merged with LLM ones
      - text: "[CH 7] I can get you the money, but I need to know why the rush."
        when: { special: { CH: { gte: 7 } } }
        effects: [ { check: { skill: speech, difficulty: 50,
                              pass: [ { add_belief: { who: player, belief: landlord-selling } } ] } } ]
      - text: "I'll pay Friday."
        effects: [ { set_flag: promised_rent }, { end_conversation: {} } ]
    hooks: [ give-spare-key, reveal-landlord-sale, adjust-trust ]   # what the LLM may invoke
    ends_when: { any: [ { flag: promised_rent }, { turns: { gte: 12 } } ] }

5.3 A conversation turn

Each character turn is one structured LLM call. The context is ordered from stable to volatile so prompt caching works:

  1. Engine rules and style guide (fixed)
  2. Story synopsis and setting tone (per payload)
  3. Character persona, SPECIAL, high-level goals and relationships (per character)
  4. Conversation goals, the hook catalogue with descriptions, beliefs and memories (per conversation)
  5. Transcript so far, plus results of the last hooks (per turn)
// structured output, validated with zod
interface CharacterTurn {
  line: string;                          // what the character says; tone unbounded, so hyperreal is welcome
  emotion?: string;
  hooks: { id: string; args: Record<string, unknown> }[];   // must be from the spec's catalogue
  playerOptions: string[];               // 2–4 suggested responses for the player
  wantsToEnd?: boolean;
}

The engine then validates and applies hooks (5.4), and merges playerOptions with the authored options whose conditions hold. Authored options win ties, and gated options show their gate ([CH 7]). The player can always leave. open Q20: should there also be a free-text "say something else" option?

5.4 Hooks: where the constructed touches the ground

Hooks are the only way a conversation changes world state (P2). The payload declares them with typed arguments, guards and effects:

hooks:
  - id: reveal-landlord-sale
    description: "Okafor admits the landlord is selling the building."   # shown to the LLM
    guard: { relationship: { who: okafor, with: player, trust: { gte: 60 } } }
    effects: [ { add_belief: { who: player, belief: landlord-selling } }, { set_flag: sale_known } ]
    once: true
  • The LLM chooses whether and when. The engine checks the guard and applies the effects deterministically. A failed guard is reported back on the next turn, so the character can react ("…no, forget I said anything").
  • A hook can fire scripted behaviours, triggers or a callout. That is how conversations "trigger scripted behaviours as well as LLM work".
  • Anything the character says without a hook is speech. It is recorded in memories, but it is not fact.

5.5 Scripted callouts

A callout is a payload-declared LLM call for moments where authored text would be too rigid, such as a dream, a radio broadcast, graffiti that changes, or a character's diary. It is fired by a trigger or behaviour effect: { callout: dream-sequence }.

callouts:
  - id: dream-sequence
    prompt: "Render the player's dream tonight, drawing on: {{memories.player.recent}}. Magical realism; 80–120 words."
    output: text                     # or a schema with hook ids, like conversations
    hooks: []                        # optional, same rules as 5.4
    cache: per-save                  # generate once per save, then fixed

5.6 Provider interface

interface LlmProvider {
  readonly id: string;               // 'claude-subscription', 'anthropic-api', 'scripted', 'replay', …
  readonly capabilities: { structuredOutput: boolean; promptCaching: boolean; streaming: boolean; maxContextTokens: number };
  complete<T>(req: CompletionRequest<T>): Promise<CompletionResult<T>>;
}
interface CompletionRequest<T> {
  purpose: 'conversation' | 'callout' | 'summary';
  system: PromptPart[];              // ordered stable → volatile
  messages: { role: 'user' | 'assistant'; content: string }[];
  schema?: ZodType<T>;               // validated engine-side regardless of provider
  maxOutputTokens?: number;
}
  • Invalid output gets one retry, then a safe fallback: an authored "they don't answer" line plus authored options only. A turn never crashes.
  • refusal stop reasons are handled the same way.

5.7 Cost

LLM calls happen only per conversation turn, per callout and per end-of-conversation summary. Exploration is free. Usage is logged per purpose and per payload so that model choice can be based on measurements.
